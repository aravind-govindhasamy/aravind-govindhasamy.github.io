## The Problem I Already Had

At Semicon Media I work on [Circuit Digest Cloud](/case-studies/circuit-digest-cloud). It started from Tiangolo's full-stack FastAPI template.

That template is very good. FastAPI, Pydantic, a generated TypeScript client, a React frontend, Docker Compose, tests. And it is free.

It also leaves a lot to you:

- **Auth you own.** Password hashing, token issuing, sign-up and reset endpoints, SMTP settings, email templates, a mail-catcher container.
- **Sessions.** An 8-day token in localStorage, with no refresh.
- **Ownership.** An `owner_id` check written by hand into every endpoint, and the hope that nobody forgets one.
- **Everything after "users and items".** Roles, teams, invitations, API keys, payments, phone codes, an admin console. Lately, an AI assistant and an MCP server too.

None of that is the product. All of it has to exist before the product can be sold.

That is the problem. Not a hypothetical one. One that has eaten a lot of my working hours.

## Four Hours, Two Architectures

At 8:50 AM, the backend talked to Postgres directly. Each request ran inside a transaction as the caller: `set role authenticated`, plus the user's JWT claims, so RLS applied.

At 12:50 PM, that was gone.

The backend now talks to Supabase over its REST API, carrying the user's own token. RLS applies because the request *is* the user. There is no database connection string in the backend at all. The secret key is used for exactly three things: verifying webhooks, recording payments, and resolving API keys.

API keys were the tricky part. A key has to act as its owner, under the owner's RLS rules. So the server gets a real Supabase session for the owner, using the secret key and an admin magic link that it verifies on the spot, then caches it and refreshes it.

Both versions worked.

The second one has fewer ways to go wrong. A backend with no database password cannot leak one.

## The Hole

This is the part I would want to know about, if I were buying.

At 11:55 AM there is a commit titled "close default-grant hole".

By default, Supabase grants `ALL` on new tables to the `anon` and `authenticated` roles. I had written column-level grants on top: users must not change their own `plan`, must not read `key_hash` on API keys, must not read `token_hash` on invitations.

They did nothing.

In Postgres, column grants only add to what a role has. A table-level `ALL` already covers every column, so the column grants next to it protected nothing.

RLS still kept users to their own rows. But their own rows were exactly the problem.

The fix: every migration now revokes Supabase's defaults first, then grants only what is needed.

And a test called `test_users_cannot_escalate` plays the attacker. It signs in as an ordinary user, takes the publishable key and that user's own token, skips my backend entirely, and calls Supabase's REST API directly. Then it tries to:

- set its own plan to `enterprise`
- read the stored hashes of API keys
- insert a payment marked `paid`
- give itself the admin role
- reset its own usage counter to zero
- call the admin metrics function, and the function that applies payment events

Every attempt has to fail, or the test fails.

These tests run against a real Supabase with the real migrations, locally and in CI. Not a mock. A mock would have said everything was fine.

![The sign-in page: on the left, the line "Only you can see your data" above a query that returns only the signed-in user's rows; on the right, sign-in by password, email code or phone code, and Continue with Google](/blog/fastapi-starter-worth-paying-for/sign-in-only-you-can-see-your-data.png)

I wanted that sentence to be true before it was decoration.

Plenty of starters turn RLS on and then query from the server with an admin key. At that point RLS protects nothing. Here, the web app, API keys and MCP clients all reach Postgres as the user.

## Roles That Hold Up

![Roles and permissions page: the built-in admin role on the left, and a matrix of resources such as items, roles, users, payments and audit against read, create, update and delete checkboxes](/blog/fastapi-starter-worth-paying-for/roles-permission-matrix.png)

Roles are a matrix: role × resource × read, create, update, delete. Role assignments can expire. A single user can be given an extra permission, or have one taken away.

One SQL function, `has_permission()`, answers the question for Postgres RLS, for FastAPI and for the UI. Three places, one answer.

Adding a protected endpoint is one parameter:

```python
@router.get("/reports", dependencies=[require_permission("reports", "read")])
def reports(db: UserDB) -> list[Report]:
    return db.table("reports").select("*").execute().data  # runs as the caller, so RLS applies
```

Organizations have owners, admins and members, invitations by email or link, and ownership transfer.

Every change to roles, permissions, members, API keys, payments and plans goes into an audit log, written by a database trigger, with who made it. Not by application code that someone might forget to call.

![The assistant page: saved chats on the left, suggested prompts such as "What did I add last?" in the middle, a Copy MCP URL button at the top right, and a note that 182 of 200 requests are left today](/blog/fastapi-starter-worth-paying-for/assistant-and-mcp-url.png)

The same tools are served as an MCP server. Claude, Cursor or any other MCP client can connect with Supabase OAuth or an API key, and work in the app as that user. Never beyond their data, because the tools go through the same RLS as everything else.

At my [guest lecture](/blog/back-at-the-podium) I said the important thing about the Circuit Digest Cloud MCP server is that the model never touches a table. It calls a tool.

Same rule here.

## Monday Night: The Freeze

The long weekend part started on Monday, 19 October, at 8:29 PM.

With a bug.

Signing out froze the browser tab.

The protected route sent signed-out users to the sign-in page with a `?redirect=` back to where they were. But the redirect fired again on every location change. Each time, it wrapped the current URL, which already had a `?redirect=` in it, inside another `?redirect=`.

Forever.

The fix: redirect once per sign-out.

The same commit redesigned the sign-in page and added a demo seed script.

## Ready for Coding Agents

The starter is meant to be extended by AI coding agents, because that is how I build now.

- `AGENTS.md` holds the security rules, the commands, the layout and the recipes. Codex, Cursor, Copilot, Windsurf and Claude Code all read it.
- Two Claude Code skills. `/add-resource` creates a migration with RLS, the router, tests, the typed client, the page and the nav entry. `/add-ai-tool` adds a tool to the assistant and the MCP server.
- `ADD_PRODUCT.md`, a checklist for an agent adding a whole feature area.
- MCP servers set up for Claude Code, Cursor and Codex: Supabase in read-only mode, shadcn/ui, Playwright, and the app's own server.

The security rules are the important part. An agent that does not know them can add an endpoint that queries with the secret key, and every test will still pass. `AGENTS.md` tells it not to before it tries.
